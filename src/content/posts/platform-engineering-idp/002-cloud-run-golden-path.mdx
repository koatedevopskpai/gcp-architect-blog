<Callout type="warn" title="The production problem this solves">
Deploying a container to Cloud Run takes a single command. **Operating** it
reliably in production takes considerably more: a least-privilege runtime
identity, an isolated Artifact Registry, SLOs mapped to user experience,
multi-window alerts that fire before the error budget is exhausted, and CI that
deploys without long-lived keys. Without these guardrails, you get an endpoint
that works today and a 2 AM page with zero context or runbook.
</Callout>

**In one line:** one blessed path for shipping a Cloud Run service —
Terraform service + runtime SA + Artifact Registry, availability **and** latency
SLOs with burn-rate alerting, and keyless CI. Applied live, then destroyed.

- **Who this is for:** platform/DevOps engineers who want the default way to
  ship services, not a bespoke one per team.
- **What you get:** a working `examples/cloud-run-golden-path` Terraform module,
  a live-deployed service, SLOs + alert, a keyless CI sample, and a 3-tier
  evidence trail.
- **Proof level:** **tier 1** — applied live. The service ran at
  `hello-5fqef65h6q-uc.a.run.app`, served HTTP 200, and took 30/30 seeded
  requests, then was torn down.
- **Evidence:** run artifacts at
  [`/evidence/cloud-run-golden-path/`](/evidence/cloud-run-golden-path/) —
  health check, service describe, request count, cost note.

```
repo ──▶ CI (keyless WIF) ──▶ Artifact Registry ──▶ Cloud Run (scale-to-zero)
                                                        │
                                                        ▼
                                        Monitoring: availability + latency SLOs
                                                        │
                                                        ▼
                                        burn-rate alert  ──▶  on-call
```

## Why this matters in production

| Daily pain | Ad-hoc "just ship it" | Golden path |
|---|---|---|
| Identity | Default compute SA (broad Editor) | Dedicated runtime SA, least privilege |
| Image management | Ad-hoc pulls from unmanaged sources | Centralized Artifact Registry repo |
| Availability | You find out when customers complain | Measured SLO + explicit error budget |
| Latency | Degrades unnoticed until incidents | p95/p99 latency beside availability |
| Alerting | Raw thresholds / manual health checks | Multi-window burn-rate alerts, less noise |
| On-call | Guesswork, missing runbooks | Terraform configuration is the runbook |
| Cost | Zombie instances, surprise bills | Scale-to-zero + FinOps labels |

Google itself frames the difference as **Reliability** and **Operational
Excellence** pillars (see the Well-Architected mapping at the bottom).

## Steps

### 1. Runtime service account + Artifact Registry

The service runs as its own identity (never the default compute SA), and images
live in one labelled registry. The runtime SA can pull images, nothing more:

```hcl
resource "google_service_account" "hello" {
  account_id   = "hello-sa"
  display_name = "hello Cloud Run runtime"
}

resource "google_artifact_registry_repository" "images" {
  location      = "us-central1"
  repository_id = "cloud-run-images"
  format        = "DOCKER"
  labels = { finops_owner = "platform", env = "demo" }
}

resource "google_artifact_registry_repository_iam_member" "reader" {
  project    = "gcp-architect-demo-2026"
  location   = var.region
  repository = google_artifact_registry_repository.images.id
  role       = "roles/artifactregistry.reader"
  member     = "serviceAccount:${google_service_account.hello.email}"
}
```

Hardening that comes free or cheap: **vulnerability scanning is on by default**
for Artifact Registry in supported regions, and tag-retention (keep last N
digests) is a one-line lifecycle policy (see the example README).

### 2. The Cloud Run service (v2) with golden defaults

```hcl
resource "google_cloud_run_v2_service" "hello" {
  name     = "hello"
  location = "us-central1"

  template {
    service_account = google_service_account.hello.email

    containers {
      image = "us-docker.pkg.dev/cloudrun/container/hello:latest"
      resources { limits = { cpu = "1", memory = "512Mi" } }
      startup_probe {
        tcp_socket { port = 8080 }
        initial_delay_seconds = 0
        period_seconds        = 5
      }
    }

    scaling { min_instance_count = 0; max_instance_count = 5 }

    # Bound stuck requests (opinionated default; tune per workload).
    timeout = "30s"

    annotations = {
      # Faster cold starts: extra CPU during startup only.
      "run.googleapis.com/startup-cpu-boost"     = "true"
      "run.googleapis.com/execution-environment" = "gen2"
    }
  }
}
```

### Golden defaults (opinionated)

| Setting | Default | Rationale |
|---|---|---|
| CPU | 1 | Predictable autoscaling |
| Memory | 512Mi | Minimum with always-allocated CPU |
| Concurrency | set at deploy (`--concurrency 80`) | Workload decision, not a module opinion |
| Timeout | 30s | Bound stuck requests |
| Execution env | gen2 | Faster, more secure default |
| Autoscaling | min 0 / max 5 | Scale-to-zero with a cost cap |
| Startup | CPU boost + TCP probe | Quick cold starts, clean admission |
| Identity | dedicated `hello-sa` | Least privilege, no default Editor |
| Registry | labels + scanning | FinOps + supply-chain hygiene |

_Treat these as sensible starting points, not universal truth — tune by workload
and load test._

<Callout type="note" title="Two gotchas from the live run">
- Memory below 512 Mi is refused when CPU is always allocated — use `512Mi` or set
  `run.googleapis.com/cpu-throttling: "true"`.
- The v2 resource places `startup_probe` **inside `containers`** (v1 puts it on
  the template).
</Callout>

### 3. Public ingress (demo) or IAP

For a demo endpoint, allow invocations:

```hcl
resource "google_cloud_run_v2_service_iam_member" "invoker" {
  project  = "gcp-architect-demo-2026"
  location = google_cloud_run_v2_service.hello.location
  name     = google_cloud_run_v2_service.hello.name
  role     = "roles/run.invoker"
  member   = "allUsers"
}
```

For a real service, put IAP or an ingress destination network policy in front —
`allUsers` is for demos only.

### 4. SLOs — the pattern from the Qiita reference

Bind a monitoring service to Cloud Run and define availability **and** latency
SLOs:

```hcl
resource "google_monitoring_service" "hello" {
  service_id   = "hello-slo"
  display_name = "Cloud Run golden path (hello)"

  basic_service {
    service_type = "CLOUD_RUN"
    service_labels = {
      service_name = "hello"
      location     = "us-central1"
    }
  }
}

resource "google_monitoring_slo" "availability" {
  service             = google_monitoring_service.hello.service_id
  slo_id              = "hello-availability"
  goal                = 0.99
  rolling_period_days = 30
  basic_sli { availability { enabled = true } }
}

resource "google_monitoring_slo" "latency" {
  service             = google_monitoring_service.hello.service_id
  slo_id              = "hello-latency"
  goal                = 0.95
  rolling_period_days = 30
  basic_sli { latency { threshold = "1s" } }
}
```

The `threshold` is a protobuf duration — `1s`, not `800ms` (the API rejects
`800ms`).

### 5. Multi-window burn-rate alert

Page before you actually exhaust the budget:

```hcl
resource "google_monitoring_alert_policy" "burn_rate" {
  display_name = "hello availability burn rate"
  combiner     = "AND"

  conditions {
    display_name = "fast burn (5m)"
    condition_threshold {
      filter          = "select_slo_burn_rate(\"${google_monitoring_slo.availability.name}\", 5m)"
      threshold_value = "14.4"
      duration        = "0s"
      comparison      = "COMPARISON_GT"
    }
  }
  conditions {
    display_name = "slow burn (1h)"
    condition_threshold {
      filter          = "select_slo_burn_rate(\"${google_monitoring_slo.availability.name}\", 1h)"
      threshold_value = "14.4"
      duration        = "0s"
      comparison      = "COMPARISON_GT"
    }
  }
}
```

### 6. Keyless CI

Same Workload Identity Federation pattern the blog itself runs on: GitHub
Actions mints a short-lived token → impersonates a deploy SA → `gcloud builds
submit` → `gcloud run deploy`. No service-account keys anywhere.

```yaml
permissions:
  contents: read
  id-token: write

steps:
  - uses: google-github-actions/auth@v2
    with:
      workload_identity_provider: projects/DEMO_PROJECT_NUMBER/locations/global/workloadIdentityPools/POOL/providers/PROVIDER
      service_account: DEPLOY_SA@DEMO_PROJECT.iam.gserviceaccount.com
  - run: gcloud builds submit --tag us-central1-docker.pkg.dev/gcp-architect-demo-2026/cloud-run-images/hello:${{ github.sha }} .
  - run: gcloud run deploy hello --image=us-central1-docker.pkg.dev/gcp-architect-demo-2026/cloud-run-images/hello:${{ github.sha }} --region=us-central1
```

The math: a 99% SLO has a 1% error budget — roughly 7.2 hours of downtime per
month. **Burning at 14.4× exhausts the budget in about 2 days** (30 ÷ 14.4), which is
rapid enough to trigger an on-call page before customers notice the impact, yet slow
enough not to fire on a
single blip. That's why multi-window (5m **and** 1h at 14.4×) is the standard:
the short window catches fast deterioration, the long window catches sustained
but smaller problems.

Wire a notification channel so the alert actually reaches someone — email or
Slack via `google_monitoring_notification_channel`, referenced from the policy's
`notification_channels`. The example wires email and defaults to
`ops@example.com` until you set `alert_email`.

## Handling the live-run gotchas

- **SLOs need traffic.** A dormant service produces no SLI data. Seed a small
  load (e.g. Cloud Scheduler hitting `/`) before you screenshot the dashboard.
- **Cold starts skew latency.** Capture a warm run; note the scale-to-zero
  baseline in the chart.
- **Cost stays tiny.** Scale-to-zero bills only when serving; my run was well
  under $0.01. The demo project has an £5 budget guardrail.
- **Teardown is part of the run.** `terraform destroy` — the demo was destroyed
  the same day it was created (FinOps rule).

## Operating it in production

1. **Traffic for SLOs:** a dormant service computes SLIs against an empty
   denominator. Drive a synthetic heartbeat (Cloud Scheduler or a Uptime Check
   hitting `/health`) so availability/latency are real.
2. **Warm vs cold latencies:** cold starts skew p95/p99. Capture warm
   steady-state runs for tuning, and watch cold starts separately in platform
   logs.
3. **Dashboards:** wire `request_count`, `request_latencies`, and the SLO burn
   into one ops dashboard — see the platform's `monitoring.tf` pattern.
4. **Canary:** `gcloud run services update-traffic hello --to-revisions
   hello-00001-xyz=90,hello-00002-abc=10` for gradual rollouts.
5. **Secrets:** mount Secret Manager references per revision — never bake
   credentials into the image.

## SLO / Security / FinOps notes

- **Security:** the service runs as a dedicated `hello-sa` (no default Editor);
  CI is keyless via WIF.
- **Cost:** scale-to-zero by default; memory capped at 512 Mi keeps the bill minimal;
  every resource is FinOps-labelled.
- **Reliability:** availability + latency SLOs and a burn alert make "is the
  service ok?" a dashboard, not a guess.

## Production checklist

Copy this into a service PR template or onboarding docs:

**Identity & delivery**
- [ ] Dedicated runtime SA (no default Editor, no shared identities)
- [ ] Keyless CI via Workload Identity Federation (zero long-lived keys)
- [ ] Artifact Registry: one repo, labels, scanning, tag retention

**Service**
- [ ] Scale-to-zero (min 0) with a strict max-instance cap
- [ ] Startup CPU boost + explicit startup probe
- [ ] Request timeout set; concurrency tuned under load

**Reliability**
- [ ] Availability and latency SLOs bound to the service
- [ ] Multi-window burn-rate alert on an active notification channel
- [ ] Synthetic/uptime traffic so SLIs are never an empty denominator

**Security**
- [ ] Runtime SA limited to `artifactregistry.reader` (+ secret accessor as needed)
- [ ] Secrets via Secret Manager per revision (never in the image)
- [ ] Public ingress (`allUsers`) only for genuine public demos

**FinOps**
- [ ] FinOps labels on every resource; service/project/billing-account budgets
- [ ] Cost attributed per service; right-sizing reviewed after load tests
- [ ] Throwaway resources torn down the same day
