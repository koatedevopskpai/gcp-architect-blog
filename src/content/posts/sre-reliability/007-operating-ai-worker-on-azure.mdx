A local test can prove the worker handles a fake SIGTERM. It cannot prove that
Container Apps delivers SIGTERM early enough for the worker to release the
message. It cannot prove that role assignments have propagated, that a revision
rollback leaves the previous revision healthy, or that a month of model calls
costs what the calculator suggested.

This post is about the difference between “the code works” and “the worker is
operable.” I am writing it before the Azure checks so the claims stay honest.
The checkboxes are the contract for publishing it.

The local suite has 49 passing tests. It covers idempotency, redelivery,
retries, timeouts, cancellation, SSE heartbeat and disconnect behaviour, and

## Shutdown: the worker has to leave before the platform kills it

Container Apps sends SIGTERM before stopping a replica. The worker should stop
taking new messages, release any in-flight message, and exit inside the grace
period. If it waits for a five-minute model call, the platform can kill it
first. The message becomes visible again, and the model is called again.

The worker uses a stop event and races it against the model call. On stop, it
nacks with visibility zero so another replica can pick the message up
immediately.

The Azure check is not “does the code have a stop event.” It is:

1. Does a revision scale-down or deployment actually deliver SIGTERM?
2. How long does the worker take to exit?
3. Does the message reappear with the expected attempt count?
4. Does the next replica complete the task?
5. Is there a duplicate model call in the trace?

The YAML setting I need to verify is the grace period on the worker's revision:

```yaml
template:
  containers:
    - name: worker
      image: "${ACR_LOGIN_SERVER}/ai-ops-worker:${IMAGE_TAG}"
  terminationGracePeriodSeconds: 30
```

The exact value is a trade-off. Too short and the worker cannot release the
message cleanly. Too long and a bad revision takes too long to drain. The
evidence is a shutdown log with timestamps, not a screenshot of the YAML.

**Status: pending live shutdown test.**

## Identity: the container should not know a secret

The API and worker use user-assigned managed identities. The identities get the
minimum roles:

| Identity | Role | Scope |
|---|---|---|
| API | `Key Vault Secrets User` | The lab vault |
| API | `AcrPull` | The lab registry |
| Worker | `Key Vault Secrets User` | The lab vault |
| Worker | `Storage Queue Data Contributor` | The task queue |
| Worker | `Cognitive Services OpenAI User` | The Azure OpenAI resource |
| Migration job | `AcrPull` | The lab registry |

The Container App references Key Vault secrets by URL and identity. The secret
value does not appear in the image, the Bicep parameters or the deployment
history.

The check is:

- `az containerapp show` shows a `secretRef`, not a value.
- The Key Vault secret list does not expose values.
- The worker can read the queue and call the model with its own identity.
- Removing a role produces a clear failure, not a retry loop that hides it.

**Status: pending live identity check.** The role assignments can take several
minutes to propagate. A first deploy that fails on a fresh role assignment is
an expected setup issue, but it still has to be recorded rather than retried
until it looks green.

## Deployment: a revision is not a release

The release path is:

1. Build and test in CI.
2. Push an immutable image tag to Azure Container Registry.
3. Run the migration as a Container Apps Job.
4. Update the API and worker revisions.
5. Wait for readiness.
6. Shift traffic to the new API revision.
7. Roll back by shifting traffic if the smoke test fails.

The migration Job matters because schema changes must happen once, before new
code serves traffic. An init container would run once per replica and hide the
failure inside the pod lifecycle. Startup DDL in the API would race across
replicas and give the runtime identity schema privileges it does not need.

The rollback matters because a redeploy is not a rollback. A redeploy can fail
for the same reason the first release failed. Shifting traffic back to the
previous revision is faster and keeps the bad revision available for
investigation.

The check is:

- A failed required check blocks a pull request.
- A failed migration stops the release before traffic moves.
- A bad revision receives no traffic after rollback.
- `/health/ready` returns 200 on the revision receiving traffic.
- The previous revision is still addressable.

**Status: pending live deploy and rollback.**

## Monitoring: measure the queue, not just the process

A worker that is running is not necessarily a worker that is making progress.
The signals I care about are:

| Signal | Why it matters |
|---|---|
| Queue depth | Work is arriving faster than it is processed |
| Age of oldest message | The queue is growing stale, even if depth looks stable |
| Outbox lag | The API accepted work the relay has not published |
| Retry count by task | A transient fault is becoming a permanent one |
| Dead-letter count | Work has exhausted its retry budget |
| Model latency | The task timeout and visibility timeout are related to it |
| Token usage per task | Cost is a reliability property when retries are unbounded |
| Trace parentage | The worker span joins the API trace for the same task |

The API and worker set `session.id` and `task.id` on spans. The useful trace is
not a single successful request; it is one API span, two worker attempts, and a
single completed task. That is how you see a redelivery without reading the
queue console.

**Status: pending Application Insights query and trace capture.**

I am not going to publish an invented monthly cost. The lab has a budget and a
teardown runbook, but the actual figure depends on model tokens, log ingestion,
minimum replicas, queue operations and how long the environment stays up.

does one *failed* request cost after retries, redeliveries and a duplicate model
call.” That is the number the reliability design is trying to bound.

## What this does not prove

Even after the checks, this is a lab. It does not prove production scale,
multi-region resilience, GPU operations or a cost-optimal architecture. It
proves the operating loop: deploy, observe, shut down, roll back and account for
the work.

call. The second is about accepting work when the queue is unavailable. This one
