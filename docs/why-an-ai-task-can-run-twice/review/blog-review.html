Why an AI Task Can Run Twice—and How I Tested Recovery

Two local failure tests show why a committed result prevents a repeated model call, while failure before the database commit can still invoke the model twice.

An AI request can finish successfully and still trigger a second model call.

The first worker gets the answer, fails before committing it, and leaves an unfinished task behind. When another worker picks up that task, it has no durable result to reuse. Retrying can repeat the model invocation—and, with a paid provider, may incur another charge.

I tested two failure windows in a local reference implementation. The difference was one database commit: a committed result let the worker skip the model; a provider response that had not been committed did not.

The tests use real PostgreSQL, an in-memory queue double and a deterministic model stub. This is code evidence for an Azure worker design, with no paid inference or live Azure recovery claim. The source download includes both tests.

The everyday version

Imagine a kitchen that receives orders on paper tickets. The cook finishes an order, but the completion mark is lost before it is recorded. The next shift sees an open ticket and makes the order again.

Now change one detail: the ticket is marked done, but nobody clears it from the rack. The next shift sees the completion mark and skips the work. The ticket returned; the order does not need cooking again.

The missing fact is not whether someone received the ticket. It is whether the work already happened. In this application, the queue carries the ticket and PostgreSQL holds the durable completion record.

The system I tested

  1. Accept: the API writes the task and its outbox intent in one PostgreSQL transaction.
  2. Publish: the publisher sends a notification to the queue.
  3. Claim: the worker locks the task row with SELECT ... FOR UPDATE and records its claim.
  4. Invoke: the worker calls the model after the claim transaction commits.
  5. Complete: the worker commits the result only if its claim token and lease are still valid.
  6. Acknowledge: the worker deletes the processed queue message.

For Azure Storage Queue, retrieving a message with Get Messages makes it invisible for the visibility timeout; it does not delete it. An undeleted message can become visible again. Microsoft’s Get Messages documentation describes that lifecycle. The local queue double lets the tests request redelivery explicitly; it does not reproduce that timing.

Two failures, two outcomes

Failure pointDurable stateOutcome in the local test
Result committed; acknowledgement failsTask is completed and result existsRedelivery is acknowledged without another model call
Model returns; result commit failsTask has an unfinished claim and no resultAfter claim expiry, redelivery invokes the model again

The first test, the post-commit acknowledgement-failure test, makes queue acknowledgement raise an error after completion. It checks that the task is already completed, redelivers the notification and asserts ai.calls == 1.

The second test, the pre-commit failure test, forces the earlier failure. Here is the actual test from that same source file:

async def test_provider_response_before_commit_can_repeat(
    repo, publisher, worker, queue, ai
):
    task = await submit(repo, publisher)
    original = repo.finish

    async def crash(*args, **kwargs):
        raise OSError("crash between provider response and commit")

    repo.finish = crash
    with pytest.raises(OSError):
        await worker.one()
    repo.finish = original
    async with repo.db.transaction() as conn:
        await conn.execute(
            "UPDATE tasks SET claim_until=now()-interval '1 s' WHERE id=$1",
            task["id"],
        )
    queue.redeliver()
    await worker.one()
    assert ai.calls == 2  # Deliberate exactly-once limitation, not hidden.
    assert (await repo.get("tenant-a", task["id"]))["status"] == "completed"

This injects an OSError at the repository completion boundary. It is not an OS process kill. The test then expires the database claim explicitly and asks the queue double to redeliver. Those shortcuts make the failure window reproducible without waiting for a real broker or killing a container.

The two model calls are the expected result. The second attempt completes the task, but it cannot recover the first answer because the first attempt never stored it. This test exercises recovery of the task while exposing the limit on deduplicating external work.

What idempotency protects

Idempotency means repeating an operation has the same intended effect. The operation matters: accepting a request, committing a result and invoking an external provider have different boundaries.

DuplicateGuard in this designRemaining limit
Client retries a submissionTenant-scoped idempotency key, payload hash and database uniquenessDoes not make worker execution happen once
Notification returns after completionTerminal-status checkRequires a committed completion record
Workers compete for unfinished workRow lock, expiring claim and per-attempt claim tokenCannot undo an external call that already started
Provider receives a repeated requestProvider-supported deduplication, where documentedDepends on that provider’s contract and retention window

Microsoft’s Idempotent Consumer pattern also distinguishes consumer deduplication from protection of downstream calls. This lab does not demonstrate provider-side deduplication or make a billing claim.

Ownership needs an expiry and a fence

The repository locks the task row with SELECT ... FOR UPDATE before deciding whether to claim it. If a live claim already exists, the worker delays processing until the claim permits another attempt. It calls the queue adapter’s nack with the calculated delay rather than acknowledging unfinished work as completed. The in-memory test double requeues immediately; it does not reproduce Azure timing.

Each new claim gets a token. Completion checks that the token still belongs to this attempt and the lease has not expired. This predicate is taken from Repository.finish:

WHERE id=$1 AND claim_token=$2 AND status='running'
AND claim_until>clock_timestamp() RETURNING *

If a worker resumes after losing its claim, that condition prevents it from overwriting the new owner’s result. If a worker dies, the claim eventually expires so another attempt can proceed. Neither mechanism reverses a model call already made by the old owner. The row lock protects the short claim transaction, not the whole model invocation. A claim token fences later database writes; it does not guarantee that an old worker stops external work immediately.

The queue visibility timeout and the database claim are separate clocks. A redelivery can arrive while the database still considers another attempt active; the worker must defer it until the claim permits another attempt.

Why the outbox does not close this window

The transactional outbox commits task acceptance and the intent to publish in one PostgreSQL transaction. A publisher can retry notification delivery after a queue outage without losing that intent. This closes the acceptance-to-publication gap; it cannot put an external model call and a local result update in one transaction.

The publisher can still send the same notification again if it fails after sending but before recording publication. The worker therefore still needs its terminal check and ownership guard. The outbox does not make the provider call and the PostgreSQL result commit one transaction.

Reproduce the two failures

Download the reference source ZIP. It includes PUBLICATION-NOTES.md, dependency locks, migrations and the tests. The deployment files are a learning reference, with known readiness, notification and release issues documented in PUBLICATION-NOTES.md. Read those notes before using them: the Azure deployment path remains unverified and is not production-ready.

Use Python 3.14 and a separate disposable PostgreSQL database whose name ends in _test. The suite truncates its task and intent tables. From the extracted azure-ai-ops-lab directory, install requirements-dev.txt in a virtual environment, set TEST_DATABASE_URL, set MIGRATION_DATABASE_URL to the same URL, and migrate with python -m alembic upgrade head.

Run the two focused tests:

python -m pytest -v tests/test_recovery.py::test_post_commit_ack_failure_skips_second_ai tests/test_recovery.py::test_provider_response_before_commit_can_repeat

Both should pass. Read their assertions: the first expects one model invocation; the second expects two. The queue fixture is a policy double even when an Azurite service is available for the separate integration tests.

Evidence and limits

On 25 October 2026, the suite finished with 47 passed and 3 skipped. Both failure-window tests passed. The skipped checks were the two Azurite integration tests (no emulator configured) and the POSIX SIGTERM process test on Windows.

The publication run is recorded in the test output and artifact manifest. The manifest identifies the source files and download by SHA-256.

This local experiment does not measure Azure queue timing, managed identity, Container Apps recovery, real model latency or cloud costs. Historical authoring checks are recorded separately in the source’s docs/VALIDATION.md; they are not substitutes for the attached publication run.

The useful result is specific: after a committed completion, a duplicate notification can be absorbed without calling the model again. Before that commit, recovery can require another invocation. When evaluating an “idempotent AI worker,” ask which side of that commit its guarantee covers.
